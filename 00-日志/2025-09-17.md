**Go map \ Location Manager中的main setting 中的一些参数意义：**
**zoom level** ：
- **定义**：决定地图的缩放等级，对应 Mapbox/OSM 的瓦片层级。
    
- **范围**：一般 0–22（0 是整个地球，22 是街道级细节）。
    
- **在 GO Map 中**：数值越大，地图越精细（能看到街道、建筑），但加载的瓦片越多，性能和流量开销也越大。

常用：
- **14–15** → 城市大范围（区级/城区）
    
- **16–17** → 城市街道（常用，能看清道路和建筑）
    
- **18–20** → 超高精度（只适合小区域，消耗大）
**World Scale**
- **定义**：控制地图在 Unity 世界中的缩放比例。
    
- **默认值**：1 → Unity 世界中的 1 米 ≈ 现实中的 1 米。
    
- **调大/调小效果**：
    
    - 如果设为 **0.5** → 地图在 Unity 中会被“压缩一半”，现实 1 米 = Unity 0.5 米。

用途：
- 调整地图和游戏对象的比例（比如你的人物模型太大/太小，可以通过调 `World Scale` 来匹配）。
    
- 避免 Unity 场景里数值过大或过小导致的物理/渲染问题。
**Desired Accuracy**
- **定义**：GPS 定位精度要求（以米为单位）。
    
- **工作原理**：传给 Unity 的 `Input.location.Start()`，用来告诉系统你需要多精确的定位。
    
- **影响**：
    
    - 数值小（比如 5–10 米）：GPS 模块会更努力定位（启用更多卫星/WiFi/基站），更耗电，但定位精度高。
        
    - 数值大（比如 100–500 米）：只要大概位置就行，耗电少，速度快。
- **10–20 米**：一般的 LBS 游戏足够（类似 Pokémon Go）。
    
- **50–100 米**：对精度要求不高的应用，比如只要城市/区级别的范围。
    
- **5 米以下**：耗电大，不推荐长期使用。

### Unity Version Control
在创建新的项目时，会有是否勾选version control。
Unity Version Control（以下简称 UVC）是一个专为游戏开发设计的版本控制系统。它的核心作用是对你的项目进行备份、版本记录和团队协作管理。
1. **完整的版本历史与回溯（时光机器）**
    
    - **有什么用？** 你项目的每一个改动都会被记录。如果你不小心删除了一个重要文件，或者写了一段导致项目崩溃的代码，你可以轻松地**回溯到任何一个之前的、正常工作的版本**。这为你提供了巨大的安全感，让你可以大胆尝试各种想法而不怕搞砸一切。
        
2. **团队协作的核心（团队协作工具）**
    
    - **有什么用？** 允许多个开发者同时在同一个项目上工作而不会互相覆盖文件。系统会自动合并你们的改动。如果改动了同一个文件，它会提示冲突并帮助你解决。没有版本控制，团队协作几乎无法进行。
        
3. **分支（Branching）与并行开发**
    
    - **有什么用？** 你可以创建项目的“平行宇宙”。例如：
        
        - `main` 分支：存放稳定、可发布的版本。
            
        - `develop` 分支：日常开发的主线。
            
        - `feature/new-enemy` 分支：专门用于开发一个新敌人，完成后合并回 `develop` 分支。
            
    - 这样，开发新功能、修复紧急线上Bug、进行实验都不会影响到主线的稳定性。
4. **资产（Asset）管理优化**
    
    - **有什么用？** 这是它相比 Git（另一个流行版本控制系统）的巨大优势。Unity 项目包含大量二进制文件（如 `.unity` 场景、`.prefab` 预制体、`.fbx` 模型、纹理等）。UVC 对此进行了深度优化，支持**智能合并、部分签出（Partial Checkout）和大文件（LFS）处理**，而 Git 处理这些文件非常笨拙且容易出错。
        
5. **职责明晰**
    
    - **有什么用？** 每一次提交都会记录是谁、在什么时候、为什么做了这个改动（需要写提交信息）。这对于排查问题、追溯责任至关重要。
#### Unity中常用的3D模型格式及其特点的详细说明
|格式|主要特点|优点|缺点|适用场景|
|---|---|---|---|---|
|**`.fbx`**|**Autodesk的行业标准交换格式**|- **功能最全面**：支持模型、材质、动画、骨骼、蒙皮、灯光、摄像机等。  <br>- **保持层级关系**：导入后保留父子层级，方便在Unity中操作。  <br>- **嵌入材质纹理**：可选项，方便单文件传输。  <br>- **广泛支持**：所有主流3D软件都完美支持导出FBX。|- 是**封闭**的专有格式（虽然广泛应用）。  <br>- 有时需要针对不同软件（如Blender）调整导出设置。|**绝大多数项目的首选**。适用于角色动画、机械动画、场景搭建等所有需要完整信息的场景。|
|**`.gltf`** / **`.glb`**|**Web上的“JPEG”格式，开放标准**|- **为Web和实时渲染优化**，加载快。  <br>- **开放标准**，无版权问题。  <br>- **包含所有资源**（.glb是二进制格式，单文件包含一切）。  <br>- 在移动设备和Web上性能优异。|- 在传统游戏工作流中支持度不如FBX成熟（但正在快速追赶）。  <br>- 某些高级特性可能依赖Unity的特定插件或版本。|**WebGL项目、移动端应用、希望使用开放格式的项目**。是从Blender等软件导出PBR材质的优秀选择。|
|**`.obj`**|**古老的几何体交换格式**|- **极其简单通用**，几乎所有软件都支持。  <br>- 人类可读的文本格式（但也可为二进制）。  <br>- 导入非常稳定，不易出错。|
（补充：.blend文件可以“实时链接”，在Unity中可以直接看到Blender中对模型的修改并实时更新（无需反复导出））
