Awake → OnEnable → Start，这是执行顺序
它们各为一个阶段，一个阶段结束了就进入下一个阶段
也就是说：所有对象的 `Awake` 都执行完，才会开始执行任何对象的 `Start`。

## 三者各自的定位

| 回调       | 调用时机                        | 调用次数                 | 典型用途                           |
| -------- | --------------------------- | -------------------- | ------------------------------ |
| Awake    | 对象创建时（即使脚本 disabled 也会调用）   | ==一次==               | ==初始化==自己、`GetComponent` 拿自身引用 |
| OnEnable | 每次对象/脚本被启用时                 | ==多次（每次 enable 都调）== | 注册事件、订阅；和 `OnDisable` 配对       |
| Start    | 第一次 Update 之前，且仅当脚本 enabled | ==一次==               | 访问别的对象（因为它们的 Awake 已跑完）        |

**架构上的核心规则：**

> 在 Awake 里初始化自己，在 Start 里访问别人。

原因：你在自己的 `Awake` 里，无法保证别的对象的 `Awake` 已经跑完。

**`[DefaultExecutionOrder]` 可以改顺序**
负数越小，越早执行。这就是用「执行顺序」来保证 特定类先于普通脚本初始化
%% 补充：还有比这些都早的 `[RuntimeInitializeOnLoadMethod]`（场景加载前就跑） %%

## 完整回调表（引擎会自动调的函数）

按常见执行顺序：

|函数|什么时候|典型用途|
|---|---|---|
|`Awake`|物体第一次被加载，且组件存在时|拿引用、初始化自己，不依赖别的脚本已经 `Start`|
|`OnEnable`|组件被启用时（含第一次）|订阅事件、开始监听|
|`Start`|第一次 `Update` 之前，且组件启用|依赖其他脚本已经 `Awake` 完的初始化|
|`Update`|每帧|输入、UI、非物理逻辑|
|`FixedUpdate`|固定时间步（默认约 0.02s）|刚体、物理相关|
|`LateUpdate`|所有 `Update` 之后每帧|摄像机跟随，避免抖|
|`OnDisable`|组件被禁用或物体销毁前|取消订阅|
|`OnDestroy`|物体/组件销毁时|收尾、释放|

各种 Update 的区别见 [[各种Update]]

## 启用 / 禁用 / 销毁的顺序

启用物体时大致是：

Awake → OnEnable → Start → (循环) Update / FixedUpdate / LateUpdate

禁用：OnDisable

销毁：OnDisable → OnDestroy

注意：

- 物体一开始是 inactive，`Awake`/`Start` 会推迟到它被激活
- 组件被关掉再打开：会再走 `OnEnable`，不会再走 `Awake`/`Start`
- `Update` 系列在组件 disabled 时不会跑
